# Decisions log

## D-001: One TypeScript app, built with Next.js (App Router)
- **Date:** 2026-11-11
- **Question:** Which framework and language for the app?
- **Chosen:** Next.js with the App Router, TypeScript throughout, one repository.
- **Why:** One language and one set of types across UI, API and database layer. One process to run. Fewest moving parts for a time-boxed exercise.
- **Trade-off:** The README says "Single Page Application". Next.js is a multi-page framework with client components. The README must state why this still meets the intent. A Vite + React SPA with a separate API is the literal match, and it was considered.

## D-002: Postgres in Docker Compose, on host port 5433
- **Date:** 2026-11-11
- **Question:** Where does the database run?
- **Chosen:** Postgres container from `docker-compose.yml`, mapped to host port `5433`.
- **Why:** The owner's native Windows Postgres already uses `localhost:5432`. Two servers on one port would clash.
- **Trade-off:** Developers must remember the non-default port. It is set in `.env.example`.

## D-003: Drizzle ORM, not Prisma
- **Date:** 2026-11-11
- **Question:** Which ORM?
- **Chosen:** Drizzle, with SQL migrations generated by `drizzle-kit`.
- **Why:** The schema stays close to SQL, the runtime is light, and migrations are plain files that can be reviewed in a PR. No separate client-generation step.
- **Trade-off:** The owner knows Prisma better, so the first hour is slower. Prisma was the alternative and is acceptable.

## D-004: Zod for every boundary
- **Date:** 2026-11-11
- **Question:** How is data validated?
- **Chosen:** Zod schemas for request bodies, the AI response, and the shapes returned from the database.
- **Why:** The AI output is untrusted input. One schema can drive validation and the AI SDK's structured output. Reviewers can read the contract in one place.

## D-005: Structured output for feedback, not tool calling
- **Date:** 2026-11-11
- **Question:** Use the AI SDK's tool calling or structured output?
- **Chosen:** Structured output. The model returns one JSON object that Zod validates.
- **Why:** Stage 1 needs one reliable object: corrections and explanations. Tool calling suits agent loops, which this product does not need yet.
- **Revisit when:** Stage 2 lets the model look up past mistakes. That is the first real tool use.

## D-006: Vitest for unit tests, Playwright for end-to-end
- **Date:** 2026-11-11
- **Question:** Which test tools?
- **Chosen:** Vitest for parsing, validation and the create-analyse-store-retrieve flow. Playwright for one browser flow.
- **Why:** Vitest is fast for the logic that matters most. Playwright tests the user-visible flow, which the README asks us to explain.

## D-007: shadcn/ui for components
- **Date:** 2026-11-11
- **Question:** Which component approach?
- **Chosen:** shadcn/ui. The components are copied into the repo, so they are reviewable code. Specific components are pending a survey.

## D-008: Branch, worktree and PR for every unit of work
- **Date:** 2026-11-11
- **Question:** How is work delivered?
- **Chosen:** One branch per unit of work, in its own git worktree. Each opens a PR with its reasoning. The owner approves and merges. No agent merges.
- **Why:** Each change can be reviewed and reverted on its own. Reasoning sits next to the code it explains.
