Calls contract C02. A successful createEntry stores the original body before any feedback call. The no-loss guarantee applies once storage succeeds; draft recovery on save failure is undecided (T01). The green card comes from the brief, without settled wording or destination.

08 / Contract

C01. Create journal

Calling screen

Journal setup, after language, level and level-based AI focus selection (D-033).

Server action name

TBD T03. Existing delegate: createJournal(input: CreateJournalInput): Promise<Journal>.

Input fields

language: "en" | "es" | "it"; level: "new" | "basic" | "intermediate" | "advanced"; focus?: string[] in the historical delegate. Product: focus steers the AI; New 1, Basic up to 2, Intermediate up to 3, Advanced up to 3 (D-033).

Zod rules

createJournalSchema is z.strictObject, so extra keys fail. Language uses localeSchema, an enum of the three values. Level uses z.enum(levels). Focus uses z.array(z.string()).max(3).default([]). Omitted or undefined focus becomes []. No minimum string length, focus allowlist, per-string maximum or uniqueness check exists. An empty string or duplicate focus string is currently accepted. These historical Zod rules do not enforce D-033: New 1, Basic up to 2, Intermediate up to 3, Advanced up to 3. Level-aware validation remains T02.

Product rule

D-033: focus is a steering input for the AI. New 1, Basic up to 2, Intermediate up to 3, Advanced up to 3. Corrections per entry stay at three, separately. D-024 supplies three to six available chips; exact values remain undecided. TBD T02: reconcile the historical schema with level-based selection limits and define chip values. There is no required intention field and no not sure level value.

Result

existing delegate resolves to C08 Journal. It inserts before returning and does not redirect. The future action's result type and redirect path are TBD T03 and T01.

Errors

.parse throws validation errors; database exceptions propagate. No application error-code enum or result union is implemented. Code mapping and learner copy are TBD T03.

09 / Contract

C02. Save entry

Calling screen

New entry. Successful save leads to the brief's green card, at a destination TBD T01.

Server action name

TBD T03. Existing delegate: createEntry(input: CreateEntryInput): Promise<Entry>.

Input fields

journalId: string; body: string; entryDate?: string.

Zod rules

createEntrySchema is z.strictObject, rejecting extra keys. journalId uses idSchema = z.uuid(). Body must satisfy body.trim().length > 0 and Array.from(body).length <= 5000. Counting uses Unicode code points, not grapheme clusters. The body is validated without trimming or rewriting the stored string. entryDate uses z.iso.date() and defaults to today's YYYY-MM-DD when omitted or undefined. The default is calculated using the server process's local year, month and day at parse time. No past-only or future-only restriction is added.

Result

existing delegate resolves to C09 Entry after the insert. No feedback call or redirect occurs in this function. Future action envelope and redirect are TBD T03 and T01.

Errors

validation errors and database exceptions propagate; there is no application error-code mapping. The data function does not perform a separate journal-existence lookup. Missing-journal error presentation is TBD T03.

Storage ordering

save the original entry before requesting feedback (D-022). Feedback failure and retry must preserve the saved entry. Draft preservation after a failed database save is TBD T01.

10 / Contract

C03. Request or retry feedback, future

Calling screen

Saved entry detail, through Get feedback or Retry; review opens the same detail screen.

Server action name

TBD T03. No feedback action or data function exists in src/lib/journal/.

Input fields

TBD T03. The operation needs the already saved entry and its journal context; whether the public input is only an entry ID is not decided. No new request shape is asserted here.

Zod rules

request validation is required by the brief; the concrete action schema is TBD T03. Existing idSchema validates UUIDs, but no feedback input schema currently uses it. The model response must be validated with Zod (D-020), with C10's constraints.

Result type

TBD T03. Feedback has states pending | ready | failed and a retry action (D-022), but there is no implemented feedback DTO, action result union or reason-code type (T04).

Execution

validate input, load the saved entry and journal, set feedback pending, make one structured model call through the provider interface, validate the response, then store ready or failed with a reason. Use OpenAI gpt-6-luna (D-021). The model performs no reads or writes itself (D-020). Additional semantic checks are T09.

Errors

invalid request or missing saved entry, provider failure, timeout and invalid model output need handling. Their code literals are TBD T03 and T04. Provider timeout and recovery behavior are T10. Persistence-failure handling is also T04 and T10; successful state storage cannot be assumed if the database write fails.

Retry

retries feedback on the same saved entry, without recreating or deleting it. Automatic retries, duplicate requests, pending retries and ready regeneration are TBD T10.

15 / Contract

C08. Journal

Using screens: Journal home, Journal overview, New entry context and Review context. toJournal explicitly returns these fields:

Field Type and representation
id string, journal identifier
language "en" | "es" | "it"
level "new" | "basic" | "intermediate" | "advanced"
focus string[], always present in the DTO. AI steering input: New 1, Basic up to 2, Intermediate up to 3, Advanced up to 3 (D-033); mapper does not enforce these limits
createdAt string, produced by Date.toISOString()

Never returned by this mapper: fields outside this allowlist, including database-native Date objects, nested entry collections, model prompts, provider responses, credentials or connection objects. This is an output allowlist, not a claim that all of those fields exist in a journal row. No intention or feedback field is returned. DTO types are declared in types.ts; the mapper does not run an output Zod schema. D-004's database-output validation policy is therefore not fully implemented in this module.

16 / Contract

C09. Entry

Using screens: Review list, Entry detail and the successful-save destination. toEntry explicitly returns these fields:

Field Type and representation
id string, entry identifier
journalId string, parent journal identifier
body string, original body as stored
entryDate string, date value returned directly from the row
createdAt string, produced by Date.toISOString()
updatedAt string, produced by Date.toISOString()

Never returned by this mapper: fields outside this allowlist, including feedback status, corrected text, corrections, failure reasons, nested journal objects, database-native Date objects, model prompts, raw provider responses or credentials. The original body is intentionally returned. There is no feedback DTO yet, so its fields, public failure detail and exclusions are TBD T04. No output Zod validation is run by toEntry, despite D-004's intended policy.

C10. Feedback response, future

Using screen: Entry detail, including entries opened through Review. Consumer: C03, then a feedback DTO whose shape is TBD T04. This is a semantic contract, not a deployable JSON Schema: exact property names and requiredness are TBD T05 because no feedback schema exists in the permitted source.

Semantic field Decided type or content Limits and unresolved details
Corrected full text Text, conceptually a JSON string (D-019) Full corrected entry; exact key and string constraints TBD T05 and T08
Corrections A collection, conceptually a JSON array of correction objects (D-019) Up to three; whether zero is valid and minimum count TBD T08
Correction original span Original span from the learner's writing (D-019) JSON representation TBD T06: quoted string versus offsets is not decided
Correction fix Text of the fix, conceptually a JSON string (D-019) Exact key, empty-value policy and length TBD T05 and T08
Correction category A category for the correction (D-019) Category list and serialized type TBD T07; do not invent an enum
Correction explanation One-line text pitched at the learner's level (D-019) Exact maximum characters, newline policy and language TBD T08
Assumed level Each response states its assumed level (D-018) Exact field name and encoding TBD T05; the four configured input levels are not automatically a decided output enum

Checks after the model returns

Using screen: Entry detail through C03. These checks belong to C10, not a separate contract record.

  1. Validate the one structured response object with Zod before it becomes ready (D-020). The final schema must express the decided corrected-text and correction requirements, including at most three corrections (D-019). Exact schema, keys and treatment of extra fields are TBD T05.
  2. On invalid model output, show the required failed feedback path with a reason and retry, retaining the saved entry (D-022 and the task brief). Reason codes are TBD T04.
  3. TBD T09: checks beyond structural validation, such as span alignment with the original entry, offset bounds, overlap, duplicate corrections and corrected-text consistency, have not been decided. They must not be described as implemented checks.
  4. Only the app stores the accepted feedback and changes its state. The model does not write to the database (D-020). No feedback persistence implementation is present at this baseline (T04).

Source and API verification notes

Existing signatures and rules above are transcribed from the pinned journal module, not proposed replacements. Current read/write functions validate inputs but do not validate DTO output with Zod. The future feedback contract remains incomplete by design where decisions are missing.

Zod 4.6.7 behavior for strict-object rejection, defaults on undefined input and refinements was checked with Context7 against the versioned Zod API source. This checks API interpretation only and adds no product decisions.
